# ADR-0003: Фоновые задачи без Celery в dev; поллинг вместо SSE для M2

**Дата:** 2026-07-08 · **Статус:** принято

## Контекст

План (§3) предусматривает Celery + Redis для длинных задач и SSE для прогресса.
На dev-машине нет Docker/Redis (ADR-0001). В M2 задачи короткие: парсинг
документа (секунды) и один LLM-вызов конспекта (5–30 с).

## Решение

- Абстракция `app/core/jobs.py`: `submit(fn, ...)`. Dev — ThreadPoolExecutor
  (2 воркера) в процессе API; тесты — синхронно (`JOBS_SYNC=1`).
  Статус живёт в БД (`GenerationJob.status/steps_json`) — интерфейс тот же,
  что будет у Celery: воркер меняет строку в БД, клиент читает.
- Прогресс в M2 — поллинг `GET /jobs/{id}` (React Query refetchInterval).
  SSE добавим в M4–M5, когда пайплайн станет многошаговым (слайды→картинки→TTS→видео).
- Переход на Celery на сервере: заменить реализацию `submit()` на `task.delay()`,
  функции воркеров уже изолированы (собственная сессия БД, идемпотентность).

## Последствия

- Долгие генерации M4–M5 в dev будут занимать процесс API — приемлемо для
  одного пользователя-разработчика; на сервере — Celery.
- При рестарте dev-API «висящие» running-задачи остаются в БД — при старте
  приложения помечаем их error (stale).
