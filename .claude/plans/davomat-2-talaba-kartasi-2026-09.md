## 0. Резюме (для тех, кто читает только это)

1. Посещаемость сейчас смоделирована как в учебном центре: «занятие» существует
   только в момент отметки, нет академических часов, типа занятия, календаря
   семестра, причин/справок, отработок. **Нормативка вуза считается в ЧАСАХ по
   ПРЕДМЕТУ** (указ КМ №824: ≥25 % часов без причины → не допущен к итоговому;
   №393: >74 ч/семестр → отчисление) — **система не может посчитать это вообще.**
2. «Цикл» — пара дат на связке курс↔группа; повторный цикл невозможен
   (`@@unique([courseId, groupId])`), преподаватель не может прикрепить группу
   другого факультета (400), студент имеет одну группу навсегда. **Гостевые
   циклы — главный сценарий заказчика — структурно заблокированы.**
3. Процент посещаемости считается в **~10 местах** бэкенда по-разному
   (null/0/100 при отсутствии отметок), рисуется в **24 местах** фронта,
   6 карт цветов статусов, 13 захардкоженных «75 %». Студент и его
   преподаватель видят разные цифры об одном человеке.
4. Экраны: плоский поток без контекста семестра/цикла; студент видит
   «пропустил», но не может **ничего сделать** (ни справку подать, ни отработать);
   ~600 строк мёртвого UI + 8 хуков + 9 живых, но никем не используемых маршрутов.
5. План: **F0 санация + единый источник фактов → F1 модель (календарь, часы,
   тип, цикл, причины) → F2 преподаватель (Yo'qlama v2, Jurnal, Sikl pasporti)
   → F3 студент (Davomat 2.0: лимиты по предметам, долги, справки) → F4 Talaba
   kartasi + Baholar (ЖН/ОН/ЯН, допуск) → F5 деканат (Davomat nazorati, циклы,
   экспорт) → F6 автоматизация и AI.** 8 вопросов заказчику в §8 — три из них
   (часы, кто ставит «sababli», HEMIS) блокируют F1.

### 1.2 Расчёты

- **Формула %** — `(present + late) / (present + absent + late + excused)`:
  **уважительная причина штрафует так же, как прогул** (в знаменателе, не в числителе).
  Определена независимо в `courses/attendance.ts:288`, `me/profile.ts:24`,
  `admin/groups.ts:54,107`, `admin/students.ts:113`, `users/service.ts:373`,
  `courses/progress.ts:371,489`, `courses/service.ts:254,592`, `timetable.ts:593`,
  `tasks/service.ts:440` — при отсутствии отметок возвращает **null / 0 / 100**
  в зависимости от файла. `avgAttendance` группы — среднее процентов, не
  pooled ratio (`admin/groups.ts:119`).
- **Клиент считает сам:** `StudentDashboard.tsx:176-180` (byCourse ∩ текущий
  семестр) и `StudentDetailPage.tsx:284-288` (невзвешенное среднее по курсам) —
  три разных числа на трёх экранах.
- **Часовой пояс — реальный баг:** `attendance.ts:35-44` и копия
  `me/profile.ts:9-18` — `from` = UTC-полночь, `to` = локальный конец дня; в

  Остальное — локальное время процесса, без `TZ` в конфиге.
- **Идентичность занятия хрупкая:** `findSession` (`timetable.ts:426`) сравнивает
  `DateTime` точно; `markByDate` по умолчанию подставляет `"09:00"`

  дубликаты при параллельной отметке.
- **Авторизация:** `markByDate` не проверяет enrollment (`timetable.ts:486`) —
  любой `studentId` можно отметить в любой свой курс; агрегаты админа не
  ограничены scope (`admin/students.ts:59-63`, `users/service.ts:357`).
- **Аудит:** `MARK_ATTENDANCE` хранит только `{count, byDate}` — ни студентов,
  ни было→стало; `setupCycle` (удаляет всё расписание группы, `timetable.ts:399`,
  не транзакционно), удаление слота, `deleteSession` — **без аудита вообще**.
  Читает аудит только SUPERADMIN.
- **Гейт очного экзамена** `markedPresentToday` (`integrity.ts:27`) — любая
  отметка PRESENT/LATE на **любом** занятии курса **сегодня**: отметился в 09:00 —

## 2. Домен: как учится медицинский вуз и что требует нормативка

**Две системы обучения в одном вузе** (подтверждено локальными актами мед.
вузов: ОмГМУ — 1–3 курсы фронтальная схема, 4–6 — цикловая):

| | Фронтальная (семестр) | Цикловая (блок) |
|---|---|---|
| Кто | 1–3 курс, постоянные группы | 4–6 курс, группа проходит кафедры по очереди; **группы других факультетов приходят на нашу кафедру** |
| Ритм | 1–2 занятия/нед × 15–18 недель | ежедневно 4–6 акад. часов × 6–20 дней |
| Единица пропуска | пара (2 ч) | **день цикла** (= целая тема) |
| Итог | ОН в середине, ЯН в сессию | зачёт/экзамен цикла **в последний день**; кафедра отчитывается в деканат **по окончании курации** (РостГМУ, п. 2.13) |
| Отработка | по графику кафедры ≥1 раз/нед., не в часы занятий (РостГМУ 2.16–2.17); лекции не отрабатываются (КемГМУ) | каждый пропущенный день — обязательно, иначе цикл не зачтён |

**Нормативка Узбекистана (то, что система обязана уметь считать):**
- **Указ КМ №824 (31.12.2020), кредит-модуль:** *«Bir fanga ajratilgan
  auditoriya soatining 25 foizini va undan ortiq soatni sababsiz qoldirgan
  talaba ushbu fandan chetlashtirilib, yakuniy nazoratga kiritilmaydi»* —
  порог в **часах по предмету**, только **без причины**. Пример из практики:
  72 аудиторных часа → лимит 18.
- **Указ КМ №393 (20.06.2017):** более **74 часов** пропусков за семестр →
  отчисление приказом ректора.
- **HEMIS (гос. система):** отметка «nb» за опоздание/пропуск; перевод в
  «sababli» — по справке **форма 095** через деканат; учёт в часах
  «sababli/sababsiz» по предмету; минимум баллов ЖН для допуска к ЯН. Если вуз
  ведёт HEMIS, любой второй журнал = двойной ввод → преподаватели бросят
  систему через неделю (**Q4**).

**Зарубежный опыт (что берём):**
- **США, клеркшипы (UC Davis, UW SOM):** учёт в **днях на блок**; максимум
  **2 дня** без отработки на 4–6-недельный блок; отработка **1:1**; плановое
  отсутствие — заявка за 6 недель, экстренное — уведомить в 24 ч; превышение →
  Incomplete и эскалация декану. → **лимит на цикл в днях, заявка на
  отсутствие как объект с согласованием.**
- **РФ мед. вузы (РостГМУ 2024):** объяснительная в день выхода + документ за
  3 рабочих дня; ежемесячный анализ деканата; при блочном расписании отчёт по
  окончании цикла. → **дедлайны справки как параметры политики, отчёт цикла.**
- **Moodle Attendance:** status sets с баллами, массовое создание сессий,
  self-recording по паролю/QR, предупреждения по порогу с письмом. → **статус-
  сеты и предупреждения по порогу**; QR у нас запрещён (уже есть FaceID+GPS
  self check-in — **Q8**).
- **Исследования (PMC8298040, PMC6897060, pmid 40064241):** посещаемость
  устойчиво коррелирует с успеваемостью в мед. образовании; **ранние
  предупреждения работают только когда за флагом следует ДЕЙСТВИЕ** (Pasco
  County: алерт без вмешательства = 0 эффекта). → флаг «в зоне риска» всегда
  порождает задачу конкретному человеку (тьютор/деканат), а не только цвет.

## 3. Sariosiyo CRM — что берём, что нет

**Берём (паттерны):**
1. `StatTile`: подпись бара **обязательна по типу** (`bar` требует `barCaption`);
   предупреждающий цвет — на подписи, не на числе.
2. **«—», а не «0 %»**, когда отметок нет («не отсутствовал — не отмечен»).
3. **Отсутствие привязано к теме + флаг «o'zlashtirildi»** (`Attendance.topicId
   + caughtUp`) — прообраз отработки; для медицины это ключевая идея.
4. Статус **«Dars bo'lmadi»** (занятие не состоялось), исключённый из знаменателя.
5. Дневные пакетные действия в календаре («Dars o'tildi / bo'lmadi»), стрелки
   «к следующему учебному дню».
6. «Bugun hal qilinsin»: группы без отметок > 3 дней → действие в один клик.
7. Оповещение **один раз, вручную, после проверки** (комментарий
   `server.js:3719` — почему отказались от авто-рассылки).
8. Базовая линия графика от `min − 5`, а не от нуля (85–95 % иначе невидимы).

**Не берём (слишком легко для вуза):** нет сущности занятия (занятие =
множество строк с одной датой), нет аудита (`markedBy/createdAt` отсутствуют,
статус правится `<select>`-ом в истории), расписание — две строки текста с
маппингом в 6 файлах, нет календаря/семестров/праздников, нет unique на
`(student, group, date)`, пороги захардкожены в JSX, нет кабинета студента,
нет отчёта/экспорта по посещаемости студентов.

## 4. Принципы Davomat 2.0

- **P1. Единица учёта — занятие с типом и часами.** Считаем в академических
  часах (так требует №824/№393), показываем в занятиях И часах.
- **P2. Контекст всегда.** «Посещаемость вообще» не существует; есть
  «по предмету за семестр» или «по циклу». Каждый экран начинается со строки
  контекста: `2026/2027 · 1-semestr · 7/18-hafta` или `Sikl 08.09–20.09 · 6/10-kun`.
- **P3. Один расчёт — один сервис.** `modules/attendance/facts.ts` — единственное
  место формулы; все роли, задачи, контроль и гейты читают его. На фронте —
  один `attendanceStatus.ts` (цвет/иконка/код/i18n) и порог только из политики.
- **P4. Три числа вместо одного «%».** (1) **sababsiz soat / limit** —
  регуляторное, главное, потому что у него есть последствие; (2) **qarz** —
  отработки к сроку; (3) **davomat %** — справочное, в таблицах.
- **P5. Отсутствие — не факт, а состояние с жизненным циклом.**
  `ABSENT → (справка: заявка → утверждено → EXCUSED)` и/или `(отработка:
  назначена → сдана → принята)`. Каждый переход — запись аудита было→стало.
- **P6. Две стороны цикла.** Принимающая кафедра отмечает; домашний факультет
  видит своих. Гостевая группа **не переезжает** — она приезжает на цикл.
- **P7. STAT DIETASI и «тихий» референс.** Одна строка итогов, списки-действия,
  цифра только там, где есть действие; кнопка говорит, что произойдёт.
- **P8. Мобильный сценарий — первый.** Преподаватель отмечает с телефона в
  палате; студент фотографирует справку с телефона.

**Гостевые циклы — права.** Цикл создаёт кафедра-хозяин (преподаватель кафедры

своих групп везде (уже так через `group.facultyId`); принимающий DEPT_ADMIN
видит **ростер и журнал цикла** на своей кафедре (сегодня `getAdminGroup` даёт
DEPT 403 — ослабляем до «цикл, не профиль группы»). Студент остаётся в своей
группе; расписание студента = слоты его группы **во всех** циклах и курсах.

```ts
attendanceFacts({ studentIds, courseId?, groupId?, period: {termId|cycleId|from,to} })
→ per (student, course): {

    zone: "OK" | "WARN" | "DANGER" | "BLOCKED",        // <warn / ≥warn / ≥max−1 занятие / ≥max
    makeup: { required, submitted, accepted },
    ratePct | null                                     // (present+late) / (held − excused); null если нет отметок
  }
+ rollups: perStudentTerm (missedH vs maxMissedHoursPerTerm), perCourse, perGroup (pooled, не среднее %)
```

## 9. Связь с редизайном «Sokin panel» (параллельная работа)

- F0/F1 этого плана — бэкенд и санация; идут **параллельно** редизайну F0/F1
  (токены, `StatTile/ListRow/Num`), конфликтов по файлам нет
  (редизайн трогает `packages/ui` и токены; мы — `apps/api`, `lib/attendance`).
- F2+ строится **на новых примитивах** (`StatTile` с `barCaption` = наш
  `LimitBar`; `ListRow` = строки предметов/долгов; `Num` = часы/время/проценты).
  Начинать F2 после редизайна F1.
- Редизайн F2.2 (`StudentDetailPage` → профиль-паттерн) и F3 (`AttendancePage`)
  **не переделывать дважды**: там применить только токены, структуру берёт этот
  план (F3/F4).

## 10. Риски

- **Двойной ввод с HEMIS** — главный риск внедрения (Q4).
- **Миграция циклов**: `CourseGroup.cycle*` → `CourseCycle` без потери
  сгенерированных сессий; сироты от мёртвых маршрутов — дедупликация до unique.
- **Часовой пояс**: зафиксировать `TZ=Asia/Tashkent` на Render и в коде
  (`lib/time.ts`), иначе «сегодня» у гейта и у журнала разойдётся.
- **Регуляторные пороги — из политики, не из кода**: если вуз считает иначе
  (например, 20 %), меняется число в `/admin/control`, а не релиз.
- **Права DEPT на гостевой цикл** — ослаблять точечно (ростер/журнал цикла), не
  открывать профиль чужой группы.
